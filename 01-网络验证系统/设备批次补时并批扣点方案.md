# 设备批次补时并批扣点方案（开发期不兼容）

## 批次11现状声明（2026-05-18）

本文件是“目标方案文档”，不是“已全部落地说明”。当前源码实况：

```text
1. 业务模式层已支持 topup_align（补时并批扣点）与 average（均摊）。
2. 账务层已写入 topup_align 对应分录子类型（charged/credit）。
3. 数据库层尚未落地 EntitlementBatch / AuthorizationLot / DeviceBinding.batch_id 迁移。
```

因此，本文中的批次表结构与状态机条目应按“后续实施目标”理解，不应误读为当前全部已上线。

## 1. 范围与原则

- 范围：同一 `user_id + project_id` 下的授权设备批次治理。
- 原则：开发期不做兼容，不保留旧逻辑分支，直接切到新模型。
- 目标：支持两类并批能力，并在账务上不失真。

## 2. 业务目标

- 目标 A：新旧批次可执行“平均时间并批”，并统一为同一批次。
- 目标 B：当新批次剩余时间更长、旧批次更短时，可对旧批次执行“补时到一致并批”，该补时必须扣点。
- 目标 C：并批后对外只保留一个有效批次视图，避免后台出现长期多批次漂移。

## 3. 统一术语

- 批次：`EntitlementBatch`，包含设备数、到期时间、等级、项目。
- 目标批次：并批时被对齐的批次（通常是新购/续费后剩余更长的批次）。
- 来源批次：被补时或被平均吸收的旧批次。
- 剩余小时：`remaining_hours = ceil((valid_until - now) / 3600)`，最小计费单位 1 小时。

## 4. 并批模式

### 4.1 平均时间并批（不新增扣点）

- 适用：运营希望“时间均摊”，不做额外补时收费。
- 计算：

```text
total_devices = sum(batch.devices)
weighted_hours = sum(batch.devices * batch.remaining_hours)
merged_hours = floor(weighted_hours / total_devices)
merged_valid_until = now + merged_hours
```

- 结果：
- 全部设备进入同一批次，统一 `valid_until = merged_valid_until`。
- 不产生新增扣点流水，仅记录并批操作审计。

### 4.2 补时到一致并批（需要扣点）

- 适用：新批次时间更长，旧批次补齐到新批次时间后再并批。
- 计算（对每个来源批次分别算）：

```text
delta_hours = target_remaining_hours - source_remaining_hours
if delta_hours <= 0: 本批次不补时

raw_points = source_devices * (delta_hours / period_hours) * unit_price
deduct_points = ceil(raw_points, 2)    # 账务两位小数，向上取整避免漏扣
```

- 结果：
- 先扣点成功，再把来源批次 `valid_until` 提升到目标批次时间。
- 对齐完成后执行并批，统一为一个批次。

## 5. 你新增的关键规则（已纳入）

- 当“新批次更长、旧批次更短”时，允许对旧批次做补时。
- 补时额度以“补到与新批次一致”为上限，不允许超补。
- 补时行为必须扣点。
- 补齐后必须并批成同一批次。

## 6. 扣点与账务防失真

## 6.1 扣点顺序

- 沿用现有钱包规则：先扣 `charged_balance`，不足再扣可用 `credit_balance`。
- 任一来源批次扣点失败，则整次“补时并批”失败并回滚。

## 6.2 账务快照

- 每次补时写一条快照，最少字段：
- `operation_type = batch_topup_align`
- `authorization_id`
- `source_batch_id` / `target_batch_id`
- `source_devices`
- `source_old_valid_until` / `target_valid_until`
- `delta_hours`
- `unit_price` / `period_hours`
- `raw_points` / `deduct_points`
- `charged_consumed` / `credit_consumed`
- `idempotency_key`

## 6.3 退款口径（中长期要求）

- 并批仅统一“展示批次”，不丢失成本来源。
- 需要保留“成本分摊层”（lot）：每次购买/补时形成独立成本 lot。
- 后续退款按 lot 的剩余时间比例退，避免“并批后无法还原扣点来源”。

## 7. 状态机（补时并批）

1. 创建并批任务（`PENDING`）。
2. 锁定授权与涉及批次（防并发）。
3. 计算每个来源批次补时差与扣点。
4. 扣点（原子事务 + 幂等键）。
5. 更新来源批次到期到目标时间。
6. 执行并批（重挂设备归属到目标批次，来源批次置 `MERGED`）。
7. 写审计与快照，任务置 `SUCCESS`。

失败即回滚并置 `FAILED`，不得出现“扣了点但没并批”。

## 8. 后台交互建议（Admin 端）

- 在“用户管理 -> 授权编辑”新增 `并批处理`，提供两种模式：
- `平均时间并批`
- `补时到一致并批（扣点）`

- 弹窗必须给出预览：
- 参与批次数、设备数
- 并批后统一到期时间
- 需扣点总额（按来源批次分项）
- 钱包可用余额与是否足额

## 9. 开发期不兼容落地要求

- 删除旧的“单授权单到期”强绑定逻辑，不再保留旧分支。
- 新接口失败信息必须可读（返回差额、缺口点数、批次明细）。
- 全链路只保留一套新口径：平均并批与补时并批。

## 10. 验收用例（最小集）

- 用例 1：新长旧短，补时成功，扣点正确，并批成功。
- 用例 2：新长旧短，余额不足，补时失败，批次不变，余额不变。
- 用例 3：多旧批次同时补时，分批计算正确，合计扣点正确。
- 用例 4：平均并批，不扣点，并批后统一时间正确。
- 用例 5：并发触发两次同请求，幂等生效，不重复扣点。
