# 授权设备升级续费与时间均分方案

## 1. 定位

本方案定义 Admin/Agent 对用户项目授权进行 `新增设备`、`续费`、`升级` 时的最终业务口径。

核心原则：

1. 开发期不做短期前端壳，不做假批次展示，不保留旧链路兼容。
2. 前端展示必须来自真实后端批次数据，不能用单条 `Authorization.valid_until` 伪造成多批次。
3. 授权治理从“改字段”升级为“批次化权益动作”。
4. 扣点必须先预览、再提交；提交必须幂等；扣点、批次变更、审计必须同事务闭环。
5. 人类视角优先：界面必须说明旧设备、新设备、到期时间、扣点和批次变化，而不是只暴露技术模式名。

## 2. 当前真实基线

当前代码已经存在旧接口能力：

```text
GET  /api/users/{user_id}/authorizations/{auth_id}/devices/add/preview
POST /api/users/{user_id}/authorizations/{auth_id}/devices/add
POST /api/users/{user_id}/authorizations/{auth_id}/renew/preview
POST /api/users/{user_id}/authorizations/{auth_id}/renew
POST /api/users/{user_id}/authorizations/{auth_id}/level-upgrade/preview
POST /api/users/{user_id}/authorizations/{auth_id}/level-upgrade
```

当前问题：

1. 仍以单条 `Authorization` 为主，缺少真实 `AuthorizationBatch` 批次表。
2. 续费只面对单个授权到期时间，不能展示多批次设备到期。
3. 升级只面对单个授权剩余时间，不能按批次分别计算差价。
4. 新增设备的 `append / average / topup_align` 是技术词，界面没有解释旧设备、新设备、到期和扣点影响。
5. 前端需要手动点击预览扣点，不符合操作直觉。
6. 当前 `append` 计费存在按周期向上取整的旧口径；V2.0 统一改为按剩余小时比例精算，避免和补时扣点口径漂移。

结论：旧接口只作为当前基线说明，V2.0 不继续在旧接口上补丁式演进。

## 3. 最终数据模型

### 3.1 Authorization

`Authorization` 保留为用户和项目的授权锚点。

职责：

1. 标识 `user_id + game_project_id` 的授权关系。
2. 保存当前聚合状态，例如总授权设备数、聚合状态、默认等级。
3. 不再作为唯一权益时间来源。

### 3.2 AuthorizationBatch

新增 `AuthorizationBatch`，承载真实权益批次。

| 字段 | 说明 |
|---|---|
| id | 批次 ID |
| authorization_id | 所属授权 |
| game_project_id | 项目 ID |
| user_id | 用户 ID |
| user_level | 本批次授权等级 |
| authorized_devices | 本批次授权设备数 |
| bound_devices | 本批次已绑定设备数，可计算或冗余快照 |
| valid_from | 批次开始时间 |
| valid_until | 批次到期时间 |
| status | active / suspended / expired / merged / cancelled |
| merged_into_batch_id | 被并入后的目标批次 |
| created_action_id | 创建该批次的动作 ID |
| updated_action_id | 最后变更动作 ID |

### 3.3 AuthorizationLot

新增 `AuthorizationLot`，承载购买、续费、补时、升级差价的成本来源。

| 字段 | 说明 |
|---|---|
| id | 成本 lot ID |
| batch_id | 归属批次 |
| authorization_id | 授权 ID |
| action_id | 来源动作 |
| lot_type | grant / add_devices / renew / topup_align / level_upgrade_diff |
| user_level | 计费等级 |
| device_count | 计费设备数 |
| valid_from | 计费开始 |
| valid_until | 计费结束 |
| paid_hours | 付费小时 |
| unit_price | 单台单周期价格 |
| period_hours | 计费周期小时 |
| raw_cost | 原始金额 |
| deducted_points | 实际扣点，向上保留 2 位 |
| charged_consumed | 充值余额消耗 |
| credit_consumed | 授信余额消耗 |

### 3.4 DeviceBinding.batch_id

`DeviceBinding` 必须增加 `batch_id`。

规则：

1. 每个设备绑定必须归属一个有效批次。
2. 设备解绑不删除批次，只释放绑定数量。
3. 并批后，相关设备的 `batch_id` 必须迁移到目标批次。
4. 不允许设备绑定游离于批次之外。

### 3.5 AuthorizationAction

新增 `AuthorizationAction`，承载动作、幂等和审计串联。

| 字段 | 说明 |
|---|---|
| id | 动作 ID |
| request_id | 请求 ID |
| idempotency_key | 幂等键 |
| user_id | 用户 ID |
| authorization_id | 授权 ID |
| action_type | 动作类型 |
| payload | 提交参数 |
| preview_snapshot | 预览快照 |
| before_snapshot | 提交前快照 |
| after_snapshot | 提交后快照 |
| accounting_snapshot | 扣点明细 |
| status | pending / committed / failed |
| error_message | 失败原因 |

## 4. 统一接口契约

V2.0 下线旧分散动作接口，统一为命令接口。

```text
POST /api/users/{user_id}/authorizations/{auth_id}/commands/preview
POST /api/users/{user_id}/authorizations/{auth_id}/commands/commit
```

所有 `commit` 必须带 `idempotency_key`。

`action_type`：

```text
add_devices
renew
level_upgrade
suspend
enable
merge_average
topup_align_merge
```

`preview` 返回必须包含：

1. `before_batches`。
2. `after_batches`。
3. `accounting.items`。
4. `total_deduct_points`。
5. `charged_consumed`。
6. `credit_consumed`。
7. `available_total_after`。
8. `enough_balance`。
9. `warnings`。
10. `human_summary`。

示例：

```json
{
  "action_type": "add_devices",
  "authorization_id": 1,
  "before_batches": [],
  "after_batches": [],
  "accounting": {
    "total_deduct_points": 0,
    "charged_consumed": 0,
    "credit_consumed": 0,
    "available_total": 0,
    "available_total_after": 0,
    "enough_balance": true,
    "items": []
  },
  "warnings": [],
  "human_summary": "新增 10 台设备，补齐旧批次后统一到期 2026-06-18，预计扣点 120.00 点"
}
```

## 5. 扣点通用规则

### 5.1 小时口径

所有剩余时间和补时时间统一按小时计算。

```text
seconds <= 0 -> 0
seconds > 0  -> ceil(seconds / 3600)，最小 1 小时
```

### 5.2 比例扣点

V2.0 统一使用剩余小时比例，不再使用“不足 1 周期按 1 周期”的旧追加口径。

```text
raw = device_count * unit_price * (paid_hours / period_hours)
deduct = ceil(raw, 2)
```

规则：

1. `ceil(raw, 2)` 表示向上保留 2 位小数。
2. 充值余额优先扣，再扣授信余额。
3. 预览和提交必须使用同一套计算函数。
4. 管理员操作是否扣点由业务策略决定，但批次变更仍必须记录动作和审计。

## 6. 新增设备

入口名称保留为 `新增设备`。

弹窗必须展示：

1. 项目名称。
2. 当前等级。
3. 当前批次列表。
4. 每个批次设备数、已绑定设备数、到期时间、剩余时间。
5. 新增设备数。
6. 新增设备购买时长或目标到期时间。
7. 处理方式说明。
8. 自动扣点预览。

### 6.1 追加新批次

技术值建议：`append_new_batch`。

说明：

```text
新增设备作为一个新批次，旧设备到期时间不变。
适合只是增加设备名额，不想改变旧设备权益时间的场景。
```

扣点：

```text
new_device_cost = new_devices * unit_price * (new_paid_hours / period_hours)
deduct = ceil(new_device_cost, 2)
```

### 6.2 平均后并批

技术值建议：`average_merge`。

说明：

```text
把旧批次剩余时间和新增设备购买时间放在一起，按设备数平均，最终合成一个统一到期批次。
旧设备时间可能变长或变短，新设备也不再单独保留到期时间。
适合想统一批次，但不想额外补齐到最长时间的场景。
```

公式：

```text
old_device_hours = sum(batch.device_count * batch.remaining_hours)
new_device_hours = new_devices * new_paid_hours
total_devices = old_devices + new_devices
average_hours = floor((old_device_hours + new_device_hours) / total_devices)
new_valid_until = now + average_hours
```

扣点：

```text
deduct = ceil(new_devices * unit_price * (new_paid_hours / period_hours), 2)
```

### 6.3 补时后并批

技术值建议：`topup_align_merge`。

说明：

```text
新增设备按目标时间购买，同时把旧的短时间批次补到同一个到期时间。
补出来的时间需要扣点。
适合希望新旧设备完全统一成一个批次、一个到期时间的场景。
```

公式：

```text
target_valid_until = 新增设备目标到期时间
for each source_batch:
  delta_hours = max(0, target_remaining_hours - source_remaining_hours)
  topup_cost = source_batch.device_count * unit_price * (delta_hours / period_hours)
new_device_cost = new_devices * unit_price * (new_paid_hours / period_hours)
deduct = ceil(new_device_cost + sum(topup_cost), 2)
```

流程红线：

1. 先扣点。
2. 再补时。
3. 再并批。
4. 任一步失败整单回滚。

## 7. 续费

入口名称保留为 `续费`。

续费必须批次化，不再只展示单个授权到期时间。

弹窗必须展示：

1. 当前批次列表。
2. 每批设备数、已绑定设备数、到期时间、剩余时间。
3. 可选择续费哪些批次。
4. 续费时长或目标到期时间。
5. 处理方式说明。
6. 自动扣点预览。

### 7.1 分别续费，保持批次

技术值建议：`renew_keep_batches`。

说明：

```text
每个选中批次分别续费，原来有几个批次，续费后仍然有几个批次。
适合不想合并批次，只想延长已有批次的场景。
```

扣点：

```text
for each selected_batch:
  renew_hours = new_valid_until - max(now, selected_batch.valid_until)
  cost = selected_batch.device_count * unit_price * (renew_hours / period_hours)
deduct = ceil(sum(cost), 2)
```

### 7.2 平均后并批续费

技术值建议：`renew_average_merge`。

说明：

```text
把选中批次的剩余时间和本次续费购买的时间统一加总，按设备数平均后合成一个批次。
适合想统一到期，但不想额外补齐短批次到最长时间的场景。
```

公式：

```text
old_device_hours = sum(batch.device_count * batch.remaining_hours)
renew_device_hours = sum(batch.device_count * renew_paid_hours)
total_devices = sum(batch.device_count)
average_hours = floor((old_device_hours + renew_device_hours) / total_devices)
new_valid_until = now + average_hours
deduct = ceil(sum(batch.device_count * unit_price * (renew_paid_hours / period_hours)), 2)
```

### 7.3 补时后并批续费

技术值建议：`renew_topup_align_merge`。

说明：

```text
选择一个目标到期时间，把短批次补到该时间，再合成一个统一批次。
补齐短批次差额需要扣点。
适合要彻底统一设备批次和到期时间的场景。
```

公式：

```text
for each selected_batch:
  delta_hours = max(0, target_remaining_hours - batch.remaining_hours)
  cost = batch.device_count * unit_price * (delta_hours / period_hours)
deduct = ceil(sum(cost), 2)
```

规则：

1. 如果目标时间低于某批次当前到期时间，不允许缩短该批次权益。
2. 并批后对外只显示一个有效批次。
3. 内部 lot 保留各批次来源，用于退款和对账。

## 8. 升级

入口名称保留为 `升级`。

升级必须按批次计算差价，不允许按完整新等级重新购买。

人类直觉：

```text
客户已经买过普通等级和剩余时间。
从普通升 VIP 时，只应该补“剩余时间内普通到 VIP 的差价”。
```

弹窗必须展示：

1. 当前等级。
2. 目标等级。
3. 当前批次列表。
4. 每批设备数、到期时间、剩余时间。
5. 每批原等级剩余价值。
6. 每批新等级剩余价值。
7. 每批差价。
8. 合计扣点。
9. 自动扣点预览。

单批次公式：

```text
old_value = device_count * old_unit_price * (remaining_hours / old_period_hours)
new_value = device_count * new_unit_price * (remaining_hours / new_period_hours)
diff = max(new_value - old_value, 0)
deduct = ceil(diff, 2)
```

多批次公式：

```text
for each active_batch:
  batch_diff = max(batch_new_value - batch_old_value, 0)
deduct = ceil(sum(batch_diff), 2)
```

降级规则：

1. 如果目标等级价格低于当前等级，扣点为 0。
2. 是否允许降级由权限控制。
3. 降级不产生返点，不回补余额。
4. 降级仍必须记录动作、审计和批次等级变更。

## 9. 前端人类视角规范

### 9.1 不允许裸露技术词

| 技术值 | 页面名称 | 人话说明 |
|---|---|---|
| append_new_batch | 追加新批次 | 新增设备单独成批，旧设备时间不变 |
| average_merge | 平均后并批 | 把旧剩余时间和新购买时间按设备数平均，合成一个批次 |
| topup_align_merge | 补时后并批 | 把短批次补到目标时间后合并，补时需要扣点 |
| renew_keep_batches | 分别续费 | 各批次分别延长，不合并 |
| renew_average_merge | 平均续费并批 | 续费时间和剩余时间平均后合并 |
| renew_topup_align_merge | 补时续费并批 | 短批次补到目标时间后合并 |

### 9.2 预览不需要点击

规则：

1. 用户修改新增设备数、目标时间、目标等级、处理方式后，前端自动 debounce 调用 preview。
2. 预览区固定显示，不用点击“预览扣点”。
3. 预览失败时显示明确原因，例如余额不足、目标时间不能早于当前批次、批次状态不可操作。
4. 确认按钮只在预览成功且余额充足时启用。

### 9.3 批次展示格式

```text
批次 A
设备：10 台，已绑定 8 台
等级：普通
到期：2026-06-18
剩余：31 天 4 小时
状态：有效
```

### 9.4 扣点展示格式

```text
新增设备费用：80.00 点
旧批次补时费用：25.20 点
等级差价费用：13.60 点
合计扣点：118.80 点
充值余额消耗：100.00 点
授信余额消耗：18.80 点
操作后可用余额：331.20 点
```

## 10. 事务和审计红线

1. 不允许扣点成功但批次变更失败。
2. 不允许批次合并成功但设备 `batch_id` 未迁移。
3. 不允许预览和提交使用两套公式。
4. 不允许同一个 `idempotency_key` 重复扣点。
5. 不允许前端展示后端不存在的批次。
6. 不允许账务中心看不到新增设备、续费、升级、补时、并批记录。
7. 不允许审计日志缺失 `user_id + authorization_id + action_id + idempotency_key` 串联。

## 11. 实施顺序

不做短期壳，按最终方案实施。

1. 数据模型：新增 `AuthorizationBatch`、`AuthorizationLot`、`AuthorizationAction`，`DeviceBinding` 增加 `batch_id`。
2. 迁移：为现有授权生成初始批次；开发期不做兼容双轨，迁移后旧字段只保留聚合或逐步下线。
3. 服务层：新增批次预览引擎，统一计算新增设备、续费、升级、平均并批、补时并批。
4. 账务层：新增 lot 与扣点流水，统一 `charged -> credit` 扣点顺序。
5. 路由层：上线统一 `commands/preview` 和 `commands/commit`，下线旧分散动作接口。
6. 前端：三个弹窗改为批次化视图，自动预览扣点。
7. 测试：覆盖新增设备、续费、升级、多批次、余额不足回滚、幂等防重扣、设备 batch_id 迁移。
8. 文档：同步数据库设计、接口清单、账务中心规则、服务层业务规则、前端操作手册。

## 12. 验收标准

1. 新增设备能清楚看到旧批次、新设备目标到期、处理方式和扣点来源。
2. 续费能看到每个批次的到期时间，并支持分别续费、平均并批、补时并批。
3. 升级按批次剩余时间计算等级差价，不按完整新等级重买。
4. 所有弹窗均自动预览扣点，不需要手动点击预览。
5. 所有批次动作都能在账务和审计中追溯。
6. 前端没有假批次，后端没有字段直改绕过动作中心。
